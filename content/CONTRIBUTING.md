# 贡献指南 (CONTRIBUTING)

感谢关注《逃离塔科夫百科全书》！本项目欢迎一切形式的贡献。

## 🧭 我们要什么样的条目

- **机制导向**：解释“是什么、为什么、怎么用”，而不是罗列攻略套路；
- **数据详实**：**能给数据的地方就写足**——具体数值、分档表、对照表都写出来，不要停在“只讲原理、不给数”。**版本更新频繁是已知代价，用三件套管住它**：① 正文开头**必须**带版本口径页眉；② 每条数值**标出来源层级**（一级 / 二级 / 社区，见[数据口径与引用说明](docs/citation.md)第四节）；③ 登记进[待收录清单](docs/roadmap.md) 的「📈 版本敏感内容」清单，按赛季复核。**查得到的就写足，别把读者推去别处再查一次**；确实查不到出处的，才写「以游戏内为准」；
- **口径可查**：新增条目的正文开头要带**版本口径页眉**（格式固定，照抄[条目模板](template.md)骨架）。**查不实的内容不许含糊过去**——登记进[数据口径与引用说明](docs/citation.md)第三节的已知未决项表，而不是自行下结论、更不要在两处写两个互斥的数字；
- **不用配图**：全站坚持纯文字 + 表格呈现（弱网可读是本站的设计前提）；
- **中英对照**：术语首次出现时给出英文名；
- **时效要标清**：**赛季 / 联赛 / 活动限定规则**这类「赛季一结束就整页作废」的内容，必须在基本信息表之后挂一条 `> 📈 **时效提醒**：……`；普通随版本微调的数值**不用挂**（页眉已覆盖）。判据与写法见[条目模板](template.md) 的「时效性标记」一节；
- **模式差异要就地标**：正文默认口径是**持久 PvP**（见[数据口径与引用说明](docs/citation.md) 第二节）；某条规则在赛季或 PvE 下**被禁用、改写、或只在单一档案成立**时，必须在正文里就地标注，不要求读者去别的页自己拼。

## ✍️ 新建条目流程

1. 查看[待收录清单](docs/roadmap.md)并认领（或在 Issue 中提议新条目）；
2. 复制[条目模板](template.md)开始撰写；
3. 保持固定骨架：基本信息表 → 核心机制 → 实战要点 → 常见错误 → 老兵经验 → 相关条目 → 回顶部；

   > **地图类条目有两套并存的体例**（都合规，按图的写法择一即可——**不要为了“看起来统一”而改名**）。
   >
   > **两套共有的骨架**：`基本信息 → 核心机制 → 区域结构 → Boss 节 → 战利品与任务 → 实战要点 → 常见错误 → 老兵经验 → 延伸阅读 → 相关条目 → 所有条目`。**差别只有一处**：
   > - **`核心打法流派` 这一节只有老图有** —— 老图体例（地面零点 / 工厂 / 海关 / 森林 / 立交桥 / 储备站 / 海岸线）在「区域结构」之后多设一节；新图体例（实验室 / 灯塔 / 街区 / 终点站 / 破冰船 / 迷宫）不设，打法内容并入「核心机制」。
   >
   > **Boss 节的命名按内容性质定，不跟体例走**（三种都合规）：
   > - `Boss：<Boss 名>`（**同图两位稳定 Boss 时写 `Boss：<A> 与 <B>`**）—— 该图有**单一或成对的固定 Boss**（工厂 Tagilla / 海关 Reshala / 森林 Shturman / 储备站 Glukhar / 海岸线 Sanitar / 迷宫 Tagilla 之影 / **立交桥 Killa 与 Tagilla**）；
   > - `Boss 与关键 AI` —— **没有单一固定 Boss**，或多个 AI 需要并列讲（地面零点 / 灯塔 / 街区 / 终点站 / 破冰船）；
   > - `关键 AI：<单位名>` —— **只有精英 AI、没有 Boss**（实验室 Raiders）。
   >
   > 两套的差别是**内容重心**而不仅是格式：老图把“打法流派”与“战利品收益”单列成节，新图不单列、把打法并入「核心机制」。**把「核心打法流派」改名为「核心机制」会把内容说错**（流派 ≠ 机制），因此此项不做统一。
   >
   > **两处特例，是有意为之而不是漏改**：① [街区](entries/streets.md) 多一节 **`核心机制差异`**——讲的是“这张图跟别的图不一样在哪”（双 Boss 同图 / Kaban 据点化防守 / Kollontay 的警棍 / 性能与节奏），因此不与「核心机制」合并；② [地面零点](entries/ground-zero.md) 属老图体例，Boss 节却是 `Boss 与关键 AI`——因为该图**没有固定 Boss**（见上一条判据）。

4. frontmatter 填写标签（参考现有条目的标签体系）；
5. 页脚三行（`**最后更新**` / `**贡献者**` / `**License**`）之间**用 `<br>` 断行**——Markdown 的普通换行会被渲染成同一行、挤成一句；
6. **参考页同样适用**——`content/docs/` 下的页面也要写完整三行页脚。此前这一区是“多数派只写一行、个别写全三行”的无规则状态，已统一；
6. 提交 PR 前，本地跑一遍校验：

```bash
python scripts/check_entries.py
```

## 🔗 一致性要求（改一处，一处不落）

新增/修改条目后，以下位置需要同步：

- [ ] `mkdocs.yml` 的 `nav` 注册；
- [ ] `entries/index.md` 总览表；
- [ ] `README.md`（根目录）与 `content/README.md` 的条目计数；
- [ ] `tags.md` 标签汇总；
- [ ] `CHANGELOG.md` 记录变更。

> CI 会运行 `scripts/check_entries.py`。除断链与结构外，它还会校验：**条目计数一致性**（全站尾行「查看全部 N 个条目」／总览页／两处 README／路径图各篇篇数之和）、**`tags.md` 的篇数与覆盖条目是否与 frontmatter 实际统计一致**、**中文正文是否残留直引号**、**总览页「按标签浏览」的 slug 是否存在且分隔符统一**。
>
> `deploy-pages.yml` 以校验为**部署前置**——校验不通过就不会上线。

## 🖥️ 本地预览与构建

想在本地看效果，三步（**顺序不能反**）：

```bash
pip install -r requirements.txt
python scripts/build_glossary.py    # ① 生成术语数据
zensical serve                       # ② 打开 http://localhost:8000
```

**为什么必须先跑 `build_glossary.py`**：站点的**术语悬浮提示**依赖 `content/javascripts/terms-data.js`，而这个文件是**从本页上方提到的[术语速查](docs/glossary.md)自动生成**的——**改术语表，提示会自动跟着变，不需要手改两处**。

它属于构建产物、**不纳入版本管理**，所以：

- **CI 会在每次部署前自动生成**（见 `.github/workflows/deploy-pages.yml`）；
- **本地若跳过这一步**，术语提示会**静默不显示**——但页面其余部分完全正常、也不会报错。**排查“提示怎么没了”时，先看这个文件在不在。**

只跑 `zensical build`（不 serve）也可以，用于确认构建无误。

## 🏷️ 发版与版本号

站点页头那枚版本徽标由主题**在浏览器里向 GitHub API 取**，取的是**最新 Release** —— **不是最新 tag**。所以两件事要一起做，只做一半徽标就不动：

```bash
# ① 在 CHANGELOG.md 顶部加条目，版本号写在条目标题里：## 2026-10（v1.72.0）
# ② 提交并推送
git push origin main
# ③ 打 tag **并建 Release**（Release 才是徽标的数据源）
git tag -a v1.72.0 -m "v1.72.0 —— 一句话主题"
git push origin v1.72.0
gh release create v1.72.0 --title "v1.72.0 —— 一句话主题" --notes-file notes.md
```

**踩过的坑（2026-10-06 实测）**：只推 tag、不建 Release，徽标会**一直停在上一版**。本站在 v1.49–v1.70 期间只改 CHANGELOG 没建 Release，页头因此长期停在 **v1.48.0**，与 CHANGELOG 差了 **23 个版本**。

**第二次踩（2026-10-07 实测）**：v1.77.0–v1.80.4 又漏了 **8 个**，徽标停在 **v1.76.1**。已用
`scripts/backfill_releases.py` 补齐（它直接读 CHANGELOG 段落当 body，并给 v1.80.1~80.3 各挑出自己那一行）。

> **补建时的坑**：**不能给 `gh release create` 传 `--target <短SHA>`** —— 实测 422
> 「`tag_name is not a valid tag` / `Release.target_commitish is invalid`」。
> 正确次序是**先把 tag 打在目标 commit 上并推送**，再建 Release（不带 `--target`）：
> ```bash
> git tag -f v1.80.0 <sha> && git push -f origin v1.80.0
> gh release create v1.80.0 --title "…" --notes-file notes.md
> ```

> **判据**：页头徽标里的版本号必须等于 `CHANGELOG.md` 最新条目括号里的版本号。不相等 → 先查最新版有没有建 Release。
> **自检命令**（一眼看出版本序列断在哪）：`gh release list --limit 40 --json tagName --jq '.[].tagName' | sort -V`

- 事实错误 → 给出复现路径（哪张图、哪个机制）；
- 措辞/链接问题 → 直接指明位置。
