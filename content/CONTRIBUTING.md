# 贡献指南 (CONTRIBUTING)

感谢关注《逃离塔科夫百科全书》！本项目欢迎一切形式的贡献。

## 🧭 我们要什么样的条目

- **机制导向**：解释“是什么、为什么、怎么用”，而不是罗列攻略套路；
- **数据详实**：**能给数据的地方就写足**——具体数值、分档表、对照表都写出来，不要停在“只讲原理、不给数”。**版本更新频繁是已知代价，用三件套管住它**：① 正文开头**必须**带版本口径页眉；② 每条数值**标出来源层级**（一级 / 二级 / 社区，见[数据口径与引用说明](docs/citation.md)第四节）；③ 登记进[待收录清单](docs/roadmap.md) 的「📈 版本敏感内容」清单，按赛季复核。**查得到的就写足，别把读者推去别处再查一次**；确实查不到出处的，才写「以游戏内为准」；
- **口径可查**：新增条目的正文开头要带**版本口径页眉**（格式固定，照抄[条目模板](template.md)骨架）。**查不实的内容不许含糊过去**——登记进[数据口径与引用说明](docs/citation.md)第三节的已知未决项表，而不是自行下结论、更不要在两处写两个互斥的数字；
- **配图与点位**：**2026-10-14 起不再禁止**（[引用说明第六节](docs/citation.md) 有变更记录）。[交互地图](maps/index.md) 是第一个用起来的栏目。**唯一要求**：能靠脚本读到的信息，**也要给一份不靠脚本的静态版**——地图页每页附的静态任务清单就是这个；
- **中英对照**：术语首次出现时给出英文名；
- **时效要标清**：**赛季 / 联赛 / 活动限定规则**这类「赛季一结束就整页作废」的内容，必须在基本信息表之后挂一条 `> 📈 **时效提醒**：……`；普通随版本微调的数值**不用挂**（页眉已覆盖）。判据与写法见[条目模板](template.md) 的「时效性标记」一节；
- **模式差异要就地标**：正文默认口径是**持久 PvP**（见[数据口径与引用说明](docs/citation.md) 第二节）；某条规则在赛季或 PvE 下**被禁用、改写、或只在单一档案成立**时，必须在正文里就地标注，不要求读者去别的页自己拼。

## ✍️ 新建条目流程

1. 查看[待收录清单](docs/roadmap.md)并认领（或在 Issue 中提议新条目）；
2. 复制[条目模板](template.md)开始撰写（模板与[标签分类](tags.md)是**编纂附件**：2026-10-22 起从读者侧栏撤出，只从本页进 —— 读者不需要在导航里看到「条目模板」）；
3. 保持固定骨架：基本信息表 → 核心机制 → 实战要点 → 常见错误 → 老兵经验 → 相关条目 → 回顶部；

   > **地图类条目有两套并存的体例**（都合规，按图的写法择一即可——**不要为了“看起来统一”而改名**）。
   >
   > **两套共有的骨架**：`基本信息 → 核心机制 → 区域结构 → Boss 节 → 战利品与任务 → 实战要点 → 常见错误 → 老兵经验 → 延伸阅读 → 相关条目 → 所有条目`。**差别只有一处**：
   > - **`核心打法流派` 这一节只有老图有** —— 老图体例（中心区 / 工厂 / 海关 / 森林 / 立交桥 / 储备站 / 海岸线）在「区域结构」之后多设一节；新图体例（实验室 / 灯塔 / 街区 / 终点站 / 破冰船 / 迷宫）不设，打法内容并入「核心机制」。
   >
   > **Boss 节的命名按内容性质定，不跟体例走**（三种都合规）：
   > - `Boss：<Boss 名>`（**同图两位稳定 Boss 时写 `Boss：<A> 与 <B>`**）—— 该图有**单一或成对的固定 Boss**（工厂 Tagilla / 海关 Reshala / 森林 Shturman / 储备站 Glukhar / 海岸线 Sanitar / 迷宫 Tagilla 之影 / **立交桥 Killa 与 Tagilla**）；
   > - `Boss 与关键 AI` —— **没有单一固定 Boss**，或多个 AI 需要并列讲（中心区 / 灯塔 / 街区 / 终点站 / 破冰船）；
   > - `关键 AI：<单位名>` —— **只有精英 AI、没有 Boss**（实验室 Raiders）。
   >
   > 两套的差别是**内容重心**而不仅是格式：老图把“打法流派”与“战利品收益”单列成节，新图不单列、把打法并入「核心机制」。**把「核心打法流派」改名为「核心机制」会把内容说错**（流派 ≠ 机制），因此此项不做统一。
   >
   > **两处特例，是有意为之而不是漏改**：① [街区](entries/streets.md) 多一节 **`核心机制差异`**——讲的是“这张图跟别的图不一样在哪”（双 Boss 同图 / Kaban 据点化防守 / Kollontay 的警棍 / 性能与节奏），因此不与「核心机制」合并；② [中心区](entries/ground-zero.md) 属老图体例，Boss 节却是 `Boss 与关键 AI`——因为该图**没有固定 Boss**（见上一条判据）。

4. frontmatter 填写标签（参考现有条目的标签体系）；
5. 页脚三行（`**最后更新**` / `**贡献者**` / `**License**`）之间**用 `<br>` 断行**——Markdown 的普通换行会被渲染成同一行、挤成一句；
   > 📅 **`最后更新` 的口径（2026-10-13 定）：写「该页**内容**的最后修改月」**（`YYYY年M月`）。
   > **机械性改动不计**——条目计数行（`查看全部 N 个条目`）、页眉基线行、同批新增条目的导航回链，改了它们**不抬**页脚月份。
   > 判据：**改动只落在页眉/页脚/计数行/纯链接行上，就算机械性改动**；只要动了正文（哪怕一行新内容），就要把月份抬到当月。
   > 这个字段不是装饰——[`scripts/check-freshness.py`](../scripts/check-freshness.py) 拿它比对全站基线，捞「版本敏感、该回头复核」的页；写成机械改动的月份会让这个信号失效。
6. **参考页同样适用**——`content/docs/` 下的页面也要写完整三行页脚。此前这一区是“多数派只写一行、个别写全三行”的无规则状态，已统一；
7. 提交 PR 前，本地跑一遍校验：

```bash
python scripts/check_entries.py
```

## 🔗 一致性要求（改一处，一处不落）

新增/修改条目后，以下位置需要同步：

- [ ] `mkdocs.yml` 的 `nav` 注册（**读者侧**进「读 / 用 / 查」三栏之一；编纂附件不进 nav）；
- [ ] `entries/index.md` 总览表；
- [ ] `README.md`（根目录）与 `content/README.md` 的条目计数；
- [ ] `tags.md` 标签汇总；
- [ ] `CHANGELOG.md` 记录变更。

> CI 会运行 `scripts/check_entries.py`。除断链与结构外，它还会校验：**条目计数一致性**（全站尾行「查看全部 N 个条目」／总览页／两处 README／路径图各篇篇数之和）、**`tags.md` 的篇数与覆盖条目是否与 frontmatter 实际统计一致**、**中文正文是否残留直引号**、**总览页「按标签浏览」的 slug 是否存在且分隔符统一**。
>
> `deploy-pages.yml` 以校验为**部署前置**——校验不通过就不会上线。

## 🖥️ 本地预览与构建

想在本地看效果，三步（**顺序不能反**）：

```bash
pip install -r requirements.txt
python scripts/build_glossary.py    # ① 生成术语数据
zensical serve                       # ② 打开 http://localhost:8000
```

**为什么必须先跑 `build_glossary.py`**：站点的**术语悬浮提示**依赖 `content/javascripts/terms-data.js`，而这个文件是**从本页上方提到的[术语速查](docs/glossary.md)自动生成**的——**改术语表，提示会自动跟着变，不需要手改两处**。

它属于构建产物、**不纳入版本管理**，所以：

- **CI 会在每次部署前自动生成**（见 `.github/workflows/deploy-pages.yml`）；
- **本地若跳过这一步**，术语提示会**静默不显示**——但页面其余部分完全正常、也不会报错。**排查“提示怎么没了”时，先看这个文件在不在。**

只跑 `zensical build`（不 serve）也可以，用于确认构建无误。

**改了任务数据之后，还要手动重跑一次物品图标**：

```bash
python scripts/gen_item_icons.py     # 联网抓 assets.tarkov.dev，全量约 5,500 张、十分钟以内
```

它**故意不进 `build_all.py` / `check_gen_drift.py`**：要联网、非确定性，放进每次构建会让门禁变慢变脆。
漏跑的后果是**新增物品没有配图** —— 前端 `onerror` 兜底成「不显示」，不破版、也不报错，很难发现。
配图是全量口径：`icons/` 里每个文件的名字就是物品 ID，数量等于物品库件数 + 那几十个任务专属道具
（只在任务端点里、不在 `items` 端点里）。判据是**两头闭合**：`item-icons.js` 映射到的每个 id 必须有
对应文件；`icons/` 里不允许出现既不在 `scripts/data/items_full.json`、也没被映射引用的孤儿 ——
`check_entries.py` 已替你对这条账。

**重抓任务数据（会改全站计数，按顺序跑）**：

```bash
python scripts/gen_quests.py --fetch      # 任务主数据 + 页面 + 详情分片
python scripts/gen_quest_graph.py --fetch # 前置边表（id 级，必须跟着重抓）
python scripts/gen_home_stats.py          # 首页速览（任务数 / 目标数）
python scripts/build_all.py               # 其余生成物 + 全套校验
```

抓完**必须同步正文里的「N 个任务 / M 条目标」**——`check_entries.py` 会逐处对账（8 处声明 + citation），
漏改一处就红。抓取脚本会打印「新增 / 移除」清单，先看清是哪一类变化，再决定要不要接受。

## 🏷️ 发版与版本号

```bash
# ① 在 CHANGELOG.md 顶部加条目，版本号写在条目标题里：## 2026-10（v1.72.0）
# ② 提交并推送
git push origin main
# ③ 一条命令搞定 tag + Release（推荐，幂等：已发过就跳过）
python scripts/release.py
#    或手工：
git tag -a v1.72.0 -m "v1.72.0 —— 一句话主题"
git push origin v1.72.0
gh release create v1.72.0 --title "v1.72.0 —— 一句话主题" --notes-file notes.md
```

### 版本粒度：按「读者能看见的一批变化」抬版本，不按提交（2026-10-26 定）

此前隐含的做法是「每次合并抬一个版本」。26 天实测下来：`v1.47.0` 起共 **151 个版本**，GitHub 上只有 **122 个 Release**（**缺 33 个**：`v1.135.1–v1.138.2`、`v1.147.9–v1.148.1` 两段，另有更早的）——规则写的是「每版必发」，实践早就不是了。

原因不复杂：**版本号太密，发版就成了提交日志的副本**，「这条结论出自 v1.148.2」这种锚定价值反而没了（v1.148.3 只改了一个逗号的加粗）。

**判据：**

| 改动性质 | 抬版本？ | 发 Release？ |
|---|---|---|
| 条目正文、数据、结构、新增页面 | **抬** | **发** |
| 门禁脚本、体积预算、生成器内部实现、CI | 一般**不抬**（除非改变了读者能看到的行为） | 随之不发 |
| 纯排版修正（加粗串位、空格、别名、措辞微调） | **不抬**，并入下一批 | 不发 |
| 规则与指南本身（本页、`citation.md`） | **不抬**，除非同一批也改了条目正文 | 不发 |

四条配套规矩：

- **一天最多一个版本**：当天所有符合第一行的改动并成一条，发一次；
- **「一个版本一个 Release」这条硬对应不取消**——它是 `release.py` 唯一能机检的部分，也是那 33 个缺口的成因（规则一旦允许例外，就会静默失效）；
- **Latest 必须等于 CHANGELOG 顶部版本**（`gh release list --limit 1` 可验）；
- **已存在的 33 个历史缺口不补**：补建只会让 Releases 页更乱，那批版本也已没有引用者；保留现状、从本规则起按新粒度执行即可。

> 这一条与下方「补建记录（2026-10-10）」不冲突：那次补的是**连续断档**（序列断了 40 个），属于发版流程没跑，不是粒度问题。

> ⚠️ **【2026-10-07 更正】这一节原先开头写的是「站点页头那枚版本徽标由主题在浏览器里向
> GitHub API 取 `/releases/latest`」—— 那是错的，现在页头根本没有版本显示。**
> 实测（v1.87.0 发版后核验）：本项目当前用的 **Material 7（经 Zensical 构建）不再渲染任何版本元素**
> —— 产物页头的 class 只有 `md-header__title` / `__topic` / `__option`（主题切换）/
> `__source`（仓库图标）/ 搜索框；**没有 `.md-version`**，而 `extra.version` 配上去也**不会**渲染
> （试过，构建产物里仍搜不到该元素）。早年那个「版本 / 星标 / 分叉」的仓库 facts 组件
> 在这个主题版本里已经没有了 —— 主题的 JS 里那段 `/releases/latest` 代码还在，但**没有组件消费它**。
>
> **所以下面两条历史经验要这样读**：
> - 「v1.49–v1.70 期间页头停在 v1.48.0，差了 23 个版本」「v1.77.0–v1.80.4 又漏了 8 个，停在 v1.76.1」
>   —— 描述的是**当年那个 facts 组件还在时**的现象，事情本身（Release 漏建）是真的，
>   但**今天已经无法用「看页头」来验证**了；
> - **Release 仍然必须建**，理由换成两条站得住的：它是这个项目在 GitHub 上**对外唯一的版本历史**
>   （读者与 AI 引用时能锚定到具体版本），也是 `scripts/release.py` 幂等判定的对象。

> **判据（可执行，不依赖页头）**：
> ```bash
> python scripts/release.py --dry-run     # 输出的版本号 == CHANGELOG 最新条目括号里的版本号
> gh release list --limit 1              # 最新 Release 的 tag == CHANGELOG 最新版本号
> gh release list --limit 40 --json tagName --jq '.[].tagName' | sort -V   # 一眼看出序列断在哪
> ```

> **补建记录（2026-10-10）**：v1.87.1 之后又出现两段断档（**v1.88.0–v1.92.0**、**v1.93.1–v1.98.1**），
> 连同一直没补的 **v1.49.0–v1.70.0**，用 `scripts/backfill_releases.py` 一并补建 **40 个** ——
> **版本序列自 v1.47.0（Release 实践起点）起已连续**；更早的 v1.0.0–v1.46.0 从无 Release 约定，不在补建范围。
> ⚠️ **补建有个坑：Latest 徽标会被带走。** GitHub 对「**新发布**的 Release」默认置为 Latest（与提交日期无关）——
> 补完 40 个旧版本后，`/releases/latest` 实测指向了 **v1.98.1**（最后一个补建的）。
> 脚本收尾已内置指回（`gh release edit <CHANGELOG 最新版> --latest`）；手工补建时别漏这步。

> **若将来要把版本号重新显示到页头**：主题不再提供该组件，需要自建 —— 从 CHANGELOG 解析出版本、
> 注入 `.md-header__inner`、并在 `extra.css` 里补样式（主题也没带 `.md-version` 的样式）。
> **务必让显示值由 CHANGELOG 生成、并加一条 CI 断言**，否则就是一个会静默漂移的第二处数字源。

## 🐛 报告问题

- 数值过期 → Issue 标注版本号；
- 事实错误 → 给出复现路径（哪张图、哪个机制）；
- 措辞/链接问题 → 直接指明位置。
