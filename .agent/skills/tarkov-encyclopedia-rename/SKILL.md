# 改名 / 术语统一

## 第零步：先判性质 —— 这一步错了，后面全错

| 情形 | 判据 | 处理 |
|------|------|------|
| **站内自相矛盾** | 两处**并列的英文注相同**，而中文名不同 | 其中必有一个是错的 → **统一** |
| **两种译名并存** | 各有来源、英文注不同 | 保留两说，正文并列 |

> **先定性，再动手。** 共存就要保留两说，矛盾就必须统一 —— 把矛盾当共存，等于把错误留下；把共存当矛盾，等于删掉一个合法译名。

## 第一步：先读规范，再动手（不要跳过）

| 读什么 | 为了拿到什么 |
|--------|-------------|
| `content/CONTRIBUTING.md` | 命名判据（Boss 节的三种命名判据、两套地图体例）—— **体例文件必须与正文同口径** |
| `content/docs/citation.md` | 该名称是否出现在未决项里（A/B 编号与页眉第三行要跟着改） |
| `content/template.md` | 条目骨架（改名若动的是标题，要确认章节结构没被破坏） |
| `mkdocs.yml` 的 `nav:` | 条目名若变了，nav 里的显示名要同步（nav 目标是路径，改名不改路径时通常无需动） |

## 第二步：核心判据

> **改名是一次「覆盖面」任务，不是一次「查找替换」。**
> 判据只有一条：**改完之后，旧名在全站还剩几处、每一处是不是「应该剩」。**

收尾动作固定为四步：

1. **全仓 grep 旧名**（含 `content/` 之外：脚本、配置、模板）。**一律大小写不敏感**（`grep -i`，或写成 `官方 *wiki` 这类带空格通配的形态）——实测同一名称会有 `官方 Wiki` / `官方 wiki` **两种拼写并存**，只查一种会**静默漏掉二十来处**；
2. **逐处判定「改 / 不改 / 已作为引文保留」**，列成表；
3. **把这张表写进 `content/CHANGELOG.md`** —— 它是唯一能让以后的人看懂「为什么还留着旧名」的地方；
4. **再读一遍替换后的句子**（见下方坑 2）。

## 第三步：关键 —— 历史记录里的旧名 ≠ 正文里的旧名

> 前者是**当时的快照**，改写它等于伪造历史；后者是**当前口径**，留着就是错误。

**站内已有先例，照抄即可**：第八篇曾由「世界规则」改名「世界与背景」——`content/CHANGELOG.md` 的**新版本条目记录了这次改名**，而**更早的历史条目至今仍写着「世界规则」**。这坐实了站规「**历史条目只做修订不做改写**」在改名场景下的处理方式。

**一个已经验证过的覆盖率判定表形态**（旧名 11 处）：

| 位置 | 处数 | 处理 |
|------|------|------|
| 正文页 + 两处标题 | 8 | **改** |
| 体例文件 `content/CONTRIBUTING.md` | 1 | **改**（体例文件必须与正文同口径） |
| roadmap 的登记条目 | 1 | **改**为「已结案」+ 补状态，旧名**作为引文保留** |
| `content/CHANGELOG.md` 历史条目 | 2 | **不改写** |

## 第三步之二：名称带「档位 / 层级」时，改名要连标注一起复核

有些名称**本身就带档位语义**——「一级来源」「官方口径」「A / B 类未决项」。这类改名**不是换词**，判据要多一层：

> **站内每处「层级标注」都是一个信任级声明**（读者、以及抓站喂给 AI 的人，据此决定信几分）。
> 旧名改了、档位不改，等于**把错误从名称搬到档位**——更难发现，危害更大。

**落点有两类，别只查一类**（实测两类共 **175 处**，单看页眉只占其一）：

| 落点 | 形态 | 实测处数 |
|------|------|----------|
| **页眉模板行** | `> 版本基线：… ｜ 数据来源：…（一级）、…（二级）` | 波及 **86 篇条目 + `content/template.md` + `content/docs/citation.md` 的模板块** |
| **行内层级标注** | ①「口径来源」两列表；② 表末**档位列**（`\| 一级（X） \|`）；③ 表注（「数值取 **X**（一级来源）」）；④ 单行标注（「来源：一级（X）。」） | 其余全部 |

**派生声明也要跟着改**：`content/docs/citation.md` 的**分级表**、`content/llms.txt` 的「资料来源分级」段、`content/docs/value-changes.md` 的「来源层级」列；再往上一层的**上游许可链**（谁授权、本站取哪个许可版本才合规）也常在同一批补。

**先验证门禁会不会红，再动手**：`scripts/check_entries.py` 的页眉断言（`HEADER_LINE1_RE`）**只校验「数据来源：」这四个字存在，不校验后续内容** —— 所以整批页眉换措辞不会被门禁误判。**这一条必须先去脚本里读正则确认，不要凭猜**（凭猜的代价是：以为要改门禁，于是把断言放宽，反而降低约束力）。



1. **改标题会改锚点。** 标题自动生成的 id 会跟着变，而 `scripts/check_entries.py` **不校验 fragment**（`LINK_RE` 会把 `#` 之后剥掉）→ **必须手工 grep 一次「指向该页的带锚点内链」**，实测为 0 才敢落地。注意区分：**显式 `<a id="..."></a>` 不受标题改名影响**，只有自动生成的 id 会变。
2. **纯替换会产生「同名连出」。** 「A 之影与 B 的强度对照」在统一成同一个名字后会变成「**X** 之影与 **X** 的强度对照」，读者会以为在说同一只。**替换完必须逐句读一遍**，需要时补「本体」二字。
3. **标点体例会被顺手破坏。** 中文正文用**全角**（，：（））。新增段落混进半角，校验脚本**不报**。可复用扫描：正则 `[\u4e00-\u9fff][,;:()][\u4e00-\u9fff]` 逐行跑一遍（排除表格行与含反引号的行），**应为 0**。别当第一个破例的人。
4. **同一名称会有大小写 / 空格变体。** 实测 `官方 Wiki` 与 `官方 wiki` 在同一站内并存；`grep "官方 Wiki"`（区分大小写）会**静默漏掉后者**，而后者多在**正文叙述句**里（「官方 wiki 的口径是……」），恰好是改动优先级最高的一类。**第一步的全仓 grep 一律加 `-i`**，收尾再用同一条命令复扫一次——命中应为 0，或只剩**有意作为引文保留**的那几处（此时要打印上下文确认，而不是把命中数当错误）。

## 第五步：执行链

```
① 全仓 grep 旧名（记下总处数；**大小写不敏感**）
② 更新派生文件：CHANGELOG 起新版本段 + 覆盖率判定表；roadmap 登记条目标「已结案」；若本批动了图标字形，`content/template.md` 的图标现状数字随批更新
③ 手工查「指向该页的带锚点内链」（应为 0 条才动标题）
④ 改名（正文 → 两处标题 → 体例文件，逐处做）
⑤ 逐句读一遍新句子（坑 2）
⑥ 跑标点扫描（坑 3，应为 0）
⑦ scripts/build_glossary.py 术语条数不变
⑧ scripts/check_entries.py 全绿
⑨ zensical build 无告警
⑩ 产物侧确认：旧名命中 0、裸竖线段落 0
⑪ 提交推送 → 线上逐条 grep（新名命中 + 旧名归零）
```

> **第 ⑪ 步的例外**：若旧名被你**作为引文**写进「更正」块或覆盖率判定表，线上会命中 —— 这是**正确**的。要打印上下文确认，而不是把命中数直接当错误。
